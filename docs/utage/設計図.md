## 1. シンプルファネル全体図（概観）

まずは全体の骨格だけ。詳細は次章以降。

> **⚠️ 重要な構成変更（2026-05-06）**
> SARUDEMOのみCV先LINEを別アカウントに分離。BO・学び家は共通LINE維持。
> 理由：SARUDEMOは契約金150万円と高額のため、個別対応比率を上げてCV率向上＆途中離脱削減を狙う。

        └─────────┬──────────┘              └──────────┬─────────┘
                  ▼                                     ▼

                  ▼                                     ▼

                  ▼                                     ▼

                  ▼                                     ▼

                  │                                     │

                  サービス享受    別人が紹介経由で
                  （ファネル外）   新規流入 → 各LPへ戻る

**ポイント**：
- **入口は2系統**（LINE① 共通 / LINE② SARUDEMO専用）
- **出口は1系統**（決済→メンバーサイトは共通基盤、タグで出し分け）
- **⑤以降の分岐**は3章参照（本人継続 vs 紹介ルート）

## 4. タグ設計（意図マップ + 命名規則）

### 4-1. タグ設計の基本思想

**タグ = 配信や表示を出し分けるためのスイッチ**。各タグは「アンケートの何の回答」または「どの行動」をきっかけに付与され、後段の「**どのシナリオを流すか／どの決済を見せるか／どのコンテンツを開放するか**」を決めるトリガーになる。

```
   配信を出し分ける軸は「2W1H」で必要十分
   ┌────────────────────────────────────────────────┐
   │  Where（どこから来た？）   → ① 流入タグ         │
   │  Who   （払える方法は？）   → ② 信用タグ        │
   │  What  （何が欲しい？）     → ③ 興味タグ        │
   │  How   （どれくらい本気？） → ④ 本気度タグ       │
   └────────────────────────────────────────────────┘
            ↓
   この4軸の組み合わせで「個別最適な体験」を機械的に作れる
   （例：source_BO × credit_black × interest_MANA × serious_high
        → BOの最短CTAシナリオ＋学び家オプ強訴求＋面談優先案内）
```

## 7. 制作ロードマップ（5ステージ・ハイブリッド）

### 7-1. 進め方の方針

タグ・メンバーサイト・決済連携・LINE基盤は**全サービスで共通の土台**。3回作り直すのは無駄。

**結論：「土台は1回でまとめて作る／サービスの縦串は1本ずつ作って確認」のハイブリッド**

```
  ❌ 完全に1サービスずつ          ❌ 3サービス全部並列
   BO全部 → SARU全部 → MANA全部     BO+SARU+MANA同時に全機能
   ・土台3回作り直し                ・確認前に作りすぎ
   ・タグ命名がブレる               ・修正コスト爆増

  ✅ ハイブリッド（推奨）
   ┌─土台を共通で1回だけ─┐  ┌─BO縦1本通す─┐  ┌─SARU/MANA追加─┐
   │ LINE連携・タグ設計   │→│ 配信〜決済   │→│ 同じ枠に流し込む│
   │ メンバーサイト枠     │  │ クライアント │  │ ※確認サイクル  │
   │ 決済連携・特商法等   │  │ 確認①      │  │   ②③         │
   └─────────────────────┘  └─────────────┘  └────────────────┘
```

### 7-3. なぜこの順番が効率的か

```
   1. 「タグ命名」を最初に固める
      ──────────────────────────
      タグは全機能の制御スイッチ。後から変えると配信・表示制御を
      全部直す羽目になる → Stage 1 ②で1時間で全部決めてしまう

   2. 「土台 → 縦串1本」の順で確認サイクルを回す
      ──────────────────────────────────────────
      箱を1個作ってBOを通すと、SARU/MANAは「中身を流し込むだけ」
      になる。1本目で構造の良し悪しが見えるので修正コストが最小

   3. UTAGE初心者は「Stage 0 慣らし」を絶対にスキップしない
      ─────────────────────────────────────────────────
      本番フォームでミスると後段の決済・タグ連動まで全部直し。
      半日のチュートリアルで操作感を掴むのが結局最速
```

### 7-4. UTAGE初心者向け：つまずきやすいポイント先回り

| ポイント | 対策 |
|---|---|
| タグ命名がブレて配信条件が壊れる | Stage 1②で命名規則を**書き出してから**作業に入る |
| フォーム→タグ連動の設定漏れ | 各フォーム作成後に**必ずテスト送信**して付与確認 |
| LINE Webhookが応答モード「チャット」のまま | Bot応答モードに切替（よくある初日ミス） |
| 決済テストを本番カードでやってしまう | Stripe/Univapayの**テストモード**を必ず使う |
| メンバーサイトのアクセス制御忘れ | エリア作成時に**タグ条件を即座に設定**（後回し禁止） |
